# Security Policy

## Supported Versions

Security fixes target the latest released version of `sshw`.

## Reporting A Vulnerability

Please report suspected vulnerabilities privately through GitHub Security Advisories for this repository.

Do not include real server passwords, private keys, passphrases, tokens, production hostnames, or production IP addresses in public issues.

## Security Model

`sshw` is a **sandbox-aware SSH wrapper**, not a strong OS sandbox. It is designed to keep SSH secrets out of prompts, shell history, plaintext config, normal output, and JSON output, and it adds:

- **Profile/home isolation.** Config, `known_hosts`, policy, audit log, and the credential keyring namespace are scoped to the active home (`--home`, `SSHW_HOME`, `--profile`, or the built-in default). Distinct profiles never share a credential namespace.
- **Server/account credential isolation.** A server endpoint owns a `default_user` and registered account map. Explicit `--user` selection resolves only registered accounts. New v3 credential identities encode the home namespace, purpose, server, user, and generation independently, and account-specific privilege credentials cannot be confused with login credentials.
- **Optional policy enforcement.** Off by default. When enabled (via `--policy` or `policy.json` `enabled`), non-default account selection requires an exact structured policy v2 `allow_accounts` entry; legacy policy v1 permits only default accounts. `run` commands and `put`/`get` paths must also match their allowlists; denials return exit code 7 and policy enforcement fails closed. A `remote:<absolute-path>` transfer literal is validated and decoded before safety or policy checks, so it cannot select a second unchecked path representation. Every present policy file is parsed strictly, so an unknown field or unsupported version is an error even when `enabled` is false.
- **Append-only audit log.** Mutating/active operations and attempted remote operations that fail during policy setup are recorded as JSONL in `audit.jsonl`, including the selected login `user`; home-scoped operations use the active home and global profile-registry mutations use the built-in default home. Cooperating `sshw` processes serialize each complete JSON record with an advisory file lock. Because audit is best-effort, a busy record lock is retried for 100 milliseconds and then the record is skipped.
- **Output and audit redaction.** Best-effort masking of secret-looking strings.

Credentials: password authentication and privilege escalation passwords store secrets only through the native OS credential store, or — opt-in — a session-only in-memory backend that never persists. At run time, the session-only backend reads login passwords from `SSHW_PASSWORD` and privilege passwords from `SSHW_PRIVILEGE_PASSWORD`, then removes both variables from this process environment. `add --password-stdin`, `account add --password-stdin`, and `privilege set --password-stdin` may read registration passwords from stdin and store them in the active credential backend; `sshw` intentionally does not provide a `--password <value>` argument. The session-only backend separates login and privilege purposes, but applies each purpose's single environment seed to whichever registered account the invocation selects, so it does not provide the per-account credential isolation of the native backend. SSH agent authentication stores no secret in `sshw`.

## Release Integrity And Provenance

Tagged releases publish platform archives plus `SHA256SUMS`. The checksum file lets users verify that downloaded bytes match the release manifest. Release jobs pin the compiler to Rust 1.97.0 and normalize archive entry names, modes, owners, timestamps, and compression headers from the release commit timestamp. Given the same input binary, timestamp, Python implementation, and compression library, packaging is byte-deterministic.

Release assets are also covered by GitHub Artifact Attestations. The platform archives are attested in the release `build` jobs, and `SHA256SUMS` is attested in the `publish` job. Users can verify provenance with GitHub CLI:

```bash
gh release download vX.Y.Z --repo Lv2dev/sshw
sha256sum -c SHA256SUMS
gh attestation verify sshw-x86_64-unknown-linux-gnu.tar.gz -R Lv2dev/sshw
```

Attestations establish where and how an artifact was built (repository, workflow, commit, and event). They do not prove the artifact is vulnerability-free or safe to run in a particular environment; consumers still need to evaluate the release contents and their own policy. Publishing is gated by the protected `release` environment, `v*` tags are protected, and immutable releases are enabled for newly created releases. A scheduled workflow audits the locked root and fuzz dependency graphs each week in addition to CI and Dependabot controls.

`sshw doctor` reports the libssh2 and OpenSSL version/status that the current binary was built to use. This is diagnostic evidence for vulnerability triage, not a security guarantee and not a replacement for checksum or attestation verification. On Windows default builds, OpenSSL may be reported as not linked because libssh2 uses the Windows WinCNG backend.

Config and profile registry relationships are validated fail-closed: a default server must exist, every server default user must reference a registered account, every account credential must belong to its exact home/purpose/server/user boundary or a non-colliding legacy server credential, and profile homes must be absolute. Config schema v1 is read as one default account without rewriting on read; the next successful mutation persists schema v2 without deleting the legacy credential. For recovery from a legacy relative-home registry, `doctor` can report the registry error and `profile remove <affected-name>` may remove only that exact entry when the remainder validates strictly. The recovery path never interprets a relative home against the current working directory; selection, list, show, default, and remote operations remain blocked until the registry is valid.

## Limitations (Not Guarantees)

These are explicitly **not** strong guarantees:

- **Delegated access, not isolation.** Anything allowed to run `sshw run` has the selected registered account's server authority. Selecting a different account can materially change remote access; when policy is enabled, non-default accounts therefore require an exact `allow_accounts` rule. A local process running as the same OS user may access the OS credential store directly.
- **Privileged execution delegates root authority.** `sshw run --as-root --yes` uses configured privilege metadata and a stored sudo password to run the original command through `sudo -S`; the password is passed over SSH channel stdin, not embedded in the command string. Normal safety and policy checks still apply to the original command, but successful execution has the target privilege user's remote authority. If the target user has a `NOPASSWD` sudoers rule, the command runs whether or not the stored password is correct, because `sudo` never consumes the password `sshw` supplies — in that configuration the stored secret is not an independent gate. `method=su` runs the command via `su - <user> -c ...` over a PTY, injecting the stored password when the `Password:` prompt appears (PTY echo is disabled so the password is not echoed back), then sending the PTY VEOF character and SSH channel EOF so the target cannot wait indefinitely for more input. The command's output and exit code are framed by start/end markers and extracted exactly, so output lines are never dropped and a missing start marker is treated as an authentication failure. Detecting the prompt still depends on the English text forced by `LC_ALL=C`, so su is more environment-sensitive than `sudo -S`; where the prompt is not recognized (a different su variant or PAM policy) su fails closed via a prompt-wait timeout rather than hanging.
- **Remote operation bounds are guardrails.** DNS resolution, all resolved-address attempts, TCP setup, and the SSH handshake share a 15-second connection deadline. After connection, `run`/`put`/`get` use a 900-second absolute deadline by default; progress does not extend it. If `run` output exceeds 16 MiB across stdout and stderr, sshw fails with exit 5 rather than returning truncated output. The remote command may already have run, so this failure is not proof that side effects did not occur. `--timeout 0` explicitly disables the operation deadline, but not the connection deadline, the 30-second su prompt wait, or the output cap. These bounds reduce accidental hangs and memory exhaustion; they are not resource isolation for the remote host.
- **Command allowlist delegates whole-program execution.** `allow_commands` matches the program name, not its arguments. Allowlisting a program is equivalent to delegating that program's full remote capability: it may read or write any file the SSH account can reach, interpret dangerous flags, or spawn subprocesses through its own features. Be especially careful with shells and interpreters (`sh`, `bash`, `python`, `perl`), file readers/copy tools (`cat`, `tar`, `find`, `rsync`, `scp`), and privilege/process tools (`sudo`, service managers). `allow_commands` is therefore a strictly stronger grant than `allow_get_paths`/`allow_put_paths`. Prefer narrow exact commands such as `uptime` or `systemctl status app`, and only allowlist programs you trust with arbitrary arguments.
- **Path allowlists are lexical.** `allow_put_paths`/`allow_get_paths` match remote paths by normalized prefix and reject `..` traversal, but they do not resolve remote symlinks or canonicalize the remote path. The `remote:` shell-preservation prefix is removed before matching and does not change these semantics. A symlink under an allowed prefix can still resolve outside it on the remote host, so the path allowlist is a guardrail, not a remote sandbox.
- **Redaction is best-effort.** Output and audit redaction catch PEM private-key blocks, `keyword=value`/`keyword: value` for common secret keywords, and bearer tokens. Loaded login and privilege passwords are deduplicated and replaced verbatim longest-first in run stdout, stderr, and the echoed JSON command, including when one secret is a prefix of the other. Very short or common passwords can over-redact unrelated output, while transformed or split secrets may still evade matching. Do not pass secrets inline on the command line. The `run` audit record stores only the program name. Treat `audit.jsonl` as sensitive regardless.
- **Environment variables are not a secret store.** The session-only backend removes `SSHW_PASSWORD` and `SSHW_PRIVILEGE_PASSWORD` from `sshw`'s process environment immediately after reading them, but the values may already be visible to the parent shell, process launch metadata, shell history, or platform diagnostics. Prefer the native credential store for long-lived secrets.
- **stdin avoids argv, not every producer leak.** `add --password-stdin` and `privilege set --password-stdin` keep registration passwords out of command-line arguments and shell history, strip one final LF/CRLF, and reject empty input. The process that produces stdin can still expose the secret through its own logs, shell history, or diagnostics, so prefer a secret manager command over inline literals.
- **File protections are best-effort on Windows.** State files are created owner-only on Unix; on Windows protection relies on the per-user directory's NTFS ACLs. The audit log is plaintext.
- **The audit log is not tamper-evident.** `audit.jsonl` is best-effort append-only JSONL with no integrity chain or signing, and a failed write is swallowed rather than aborting the operation. Anyone who can write the home directory can edit or delete entries, so use it as an operational record, not as forensic evidence.
- **Non-UTF-8 `known_hosts` files are unsupported.** Current releases read and write the active home's `known_hosts` through Rust file I/O, including Windows paths with non-ASCII characters. The file contents are still parsed as UTF-8 OpenSSH known-host entries; invalid UTF-8 causes `trust`/`run`/`put`/`get` to fail closed because host-key verification cannot proceed.
- **No OS-level sandboxing.** `sshw` does not constrain the remote host or the local process beyond the policy allowlist. Stronger per-OS sandbox backends are a possible future extension behind the existing `Sandbox` trait.
- **Concurrent-write coordination is advisory.** Cooperating `sshw` processes serialize home mutations with `.sshw.lock`, profile registry mutations with `.profiles.lock`, and audit records by locking `audit.jsonl`. The implementation uses Rust 1.89 standard-library file locks. State-mutation lock acquisition is bounded at 5 seconds; audit uses the shorter best-effort bound above. Config and registry saves also compare the bytes originally loaded and reject a changed revision before writing. OS advisory locks do not stop another program, a same-user process that ignores the protocol, or every network-filesystem anomaly; such writers can still race the final compare/write window or edit state afterward. The locks prevent normal concurrent `sshw` invocations from silently losing updates, not hostile local tampering.

## Residual Risk Register

Last reviewed: 2026-08-31. Next review: 2026-11-30. These risks are accepted for the current threat model and must be reviewed when the connection, storage, account, policy, redaction, or release pipeline changes.

| Residual risk | Current control and decision |
| --- | --- |
| OS name-resolution cancellation | The caller stops waiting at the shared connection deadline, but the standard-library resolver worker cannot be forcibly cancelled and may finish later inside the process. It receives only the requested host and port, and no subsequent TCP or SSH work begins from that timed-out attempt. |
| Release build variance | Normalized packaging makes identical input bytes deterministic, but runner images, native libraries, linkers, Python/zlib versions, and platform toolchains mean the project does not claim end-to-end bit-for-bit reproducibility across independent builds. Exact Rust pinning, locked dependencies, checksums, protected publishing, and attestations provide the current provenance controls. |
| Profile namespace rebinding | A registered profile id, an ad-hoc `--home`, and a re-added profile are deliberately distinct credential namespaces even when paths match. `profile add --force` preserves the id for the same normalized home, but remove/re-add creates a fresh namespace and old keyring entries are not automatically rebound; this prevents an untrusted home from claiming another profile's credentials. |
| Account selection authority | Registered accounts on one endpoint may have different remote privileges. Alias-only calls use `default_user`; explicit non-default selection is exact and, under policy enforcement, requires a structured server/user allowlist entry. Policy remains a guardrail rather than an OS sandbox. |
| Post-publish durability uncertainty | Permissions and file data are finalized before atomic rename and the parent directory is synced afterward where supported. If that final sync fails, the visible file may be newer than the crash-durable directory entry. sshw reports the uncertainty and conservatively retains both old and new credential generations; this can leave a stale keyring entry, but avoids deleting the only secret a post-crash old or new config may reference. |
| Short exact secrets | Verbatim masking has no minimum length because leaking a short password is still a credential disclosure. A short/common login or privilege password can therefore replace unrelated output text; use strong unique credentials and treat redacted output as intentionally lossy. |
| Cooperative local coordination | Advisory locks and revision checks cover cooperating `sshw` processes, not hostile same-user writers or every network-filesystem behavior. This remains accepted because the local same-user boundary is outside the claimed sandbox. |
| Best-effort semantic controls | Redaction cannot understand every shell representation, policy paths remain lexical and do not resolve remote symlinks, and session environment variables may be exposed by their parent process. Stored credentials, narrow allowlists, synthetic diagnostics, and the documented limitations remain required. |
| Historical release immutability | Repository immutable-release settings apply to newly created releases; pre-existing releases are not retroactively marked immutable. Protected tags, checksums, and artifact attestations remain the verification path for those releases. |

## Stable Exit Codes

sshw's own failures map to stable exit codes for agent consumption: `2` safety, `3` config, `4` auth, `5` ssh, `6` io, `7` policy, `9` usage (invalid CLI arguments, detected before any command runs; kept distinct from safety/2), `1` unknown. A successful `run` whose remote command exits non-zero returns `8` — kept distinct from the operational codes so a remote command's status can never be mistaken for an sshw failure. The real remote status is available via `run --json` (`exit_status`).
